[Strategic Mode]

Neither, until two things are known, and they are not preferences. They are the
factors the decision turns on.

The first is recoverability. If a deleted project can be restored from a trash
state for some period, the cost of a mistaken delete is a few seconds of
annoyance and undo is the better design, because it keeps the common path clear.
If deletion is permanent and the project holds work the user cannot reproduce,
the cost of a mistake is unbounded and a confirmation earns its interruption.
The question is not which pattern is nicer. It is whether the system can undo
the thing at all.

The second is how often it happens and to whom. If deleting a project is
something an owner does once a quarter, a confirmation costs almost nothing and
buys protection against the one occasion that matters. If it is routine cleanup
done in batches by people fluent in the product, every confirmation becomes a
reflex click, and a reflex click protects nobody: the dialog has trained the
user to dismiss it, which is worse than nothing because it also carries the
appearance of safety.

So: recoverable, use undo and no dialog, whatever the frequency. Permanent and
rare, use a confirmation that states what is about to be lost rather than asking
whether the user is sure. Permanent and frequent, the design is wrong upstream
and the fix is to make it recoverable, because no dialog survives repetition.

The one combination to avoid is both. A confirmation followed by an undo tells
the user the action was dangerous and then that it was not, and the dialog is
the part that stops being read.

shared resources, which would change what recoverable means
